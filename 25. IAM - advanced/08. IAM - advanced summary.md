# Important concepts

- AWS organizations and IAM as a corporate building
  - Organization: the entire company campus
  - Organizational Units: the departments
  - IAM roles/users: individual employees
  - SCPs / permissions boundaries: security rules deciding which rooms anyone can access

## 1. Multi-account structure [AWS organizations]

- Organization: top-level umbrella
  - centrally manage, govern and pay for multiple AWS accunts
- Management account [formerly master account]
  - single parent account that created the organization
  - pays the bills and manages policies
  - IMMUNE to SCP
- Member accounts: all other AWS accounts inside the organization
  - separate accounts for `production`, `staging`, `security`, and `shared services`
- Organization root: starting container at the very top of your org's hierarchy
  - holds all your OUs and accounts
- Organization unit [OU]: folder used to group related AWS accounts together
  - ex: `prod OU` or `Sandbox OU`
  - apply rules to entire department at once, rather than one account at a time

## 2. Core identities [Who is making the request?]

- Principal: any entity allowed to make an API request to AWS
  - person, application, AWS service
- Root user: all-powerful original ownser of a single AWS account created with the sign-up email
  - best practice: lock it away with MFA and never use it for daily work
- IAM user: permanent, long-term identity created inside a single AWS account fopr a single person
- IAM group: a folder for IAM users [`devs` or `admins`]
  - allows to assign the same permissions to many users at once
  - ATTENTION: groups can only hold IAM users - NEVER IAM roles or other groups
- IAM role: a temporary security badge that anyone/anything can assume to get temporary credentials

## 3. Policies and guardrails [What are they allowed to do?]

- Identity-based policy: JSON permission document attached to an IAM user, group or role stating what that identity is allowed to do
- Resource-based policy: JSON permission doc attached directly to AWS resource [ex: s3 bucket] stating who is allowed to access that specific resource
- Service control policy [SCP]: organization-wide guardrails attach to the root, an OU, or a member account
  - sets the absolute maximum celing for everyone in those accounts
  - it just sets the CEILING, it doesn't GRANT permissions
- Resource control policy [RCP]: similar to SCP, except it sets ceiling on RESOURCES
- Permissions boundary: granular guardrail attached to an individual IAM user or role inside an account
  - sets ceiling, without granting permissions
  - makes it safe for devs to create their own roles without escaling privileges

### SCP vs. Permission Boundary

- Both set a max permission without granting it
- SCPs:
  - org-wide guardrails attached to entire AWS accounts or OUs
- Permission boundary:
  - granular guardrails attached to individual IAM users or roles inside a single account

| Feature                     | SCPS                                                                        | IAM Permissions boundaries                                            |
| --------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Where it lives              | AWS organizations                                                           | AWS IAM [inside a single AWS account]                                 |
| Affects root user?          | Yes, restricts every principal in a MEMBER account, including the root user | No, can't be attached to an AWS account root user                     |
| Affects management account? | No, SCPs never restrict the organizations management account                | Yes, can be attached to IAM users/roles inside the management account |
| Use case                    | Company-wide guardrails                                                     | Delegating IAM permissions safely                                     |

## Modern access and policy evaluation terms

- AWS IAM identity center [formerly AWS SSO]
  - modern, recommended way to give human employees SSO across all AWS accounts in your ORG using one login
